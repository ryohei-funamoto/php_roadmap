## 良かった点

- **疑問をそのままにせず確かめている。** 「`0` や空の配列など、他の falsy な値も表示されないのか」と質問し、理由（文字列に変換されること）まで理解できた。
- **実行結果をコメントに書き残している。** 後で見返したときに、コードと結果を対応させやすい。
- **書き方の細部に気を配っている。** `{$price}` の波かっこなど、トラブルを防ぐ書き方を自然に選べている。

## 補強するとよい点

1. **`print_r` では区別できない値を意識する**
   - `true` / `1` / `"1"` → どれも `1` と表示される
   - `8.5` / `"8.5"` → どれも `8.5` と表示される
   - `false` / `null` / `""` → どれも何も表示されない

   型が重要な場面（条件分岐のデバッグなど）では、`var_dump` を使う習慣をつける。
2. **実行結果のコメントは、実際に実行して写す**
   一度、手入力のコメントと実際の出力が食い違っていた（`testlint(1)` と `testint(1)`）。
   予想と結果を分けて書く今の形式は良いので、「結果」は必ず実行してから書くようにする。

## 次の分野へのつながり

- 型の変換（`true` → `"1"`、`null` → `""`）は、次の「Data Types」と「Casting Data Types」で体系的に学ぶ。
- `var_dump` は今後のデバッグで毎回使うので、出力の読み方（`string(3)` の数字は文字数ではなくバイト数、など）にも慣れていく。
